# Anki oracle

This tool generates the reference behaviour for engram's Anki-compatible note type engine. It
drives the pinned Anki Python package (`anki==26.9.3`, the release `26.09.3` of
`ankitects/anki`) to build a collection from placeholder content, renders every card through
Anki's own code, and writes the result to `internal/notetype/testdata/anki/`:

- one `.apkg` fixture per rule group, in the package format the group needs;
- one golden JSON per fixture group, holding exactly what Anki returned.

The goldens are the expected behaviour for the Go ports of `template.rs`,
`template_filters.rs`, `cloze.rs`, `cardgen.rs`, the audio/TTS/LaTeX rendering and
`typeanswer.rs`. A test never edits a golden file by hand: it is regenerated here.

No real deck content is committed. Every field text below is written in `generate.py`, and every
media file is generated byte for byte by the same script.

CI does not run Python. The packages and goldens are committed, and this tool is run only when
the fixtures are added or Anki's pinned version moves.

## Verifying a produced package

`verify_package.py` imports a `.apkg` produced by engram into a fresh collection with
`anki==26.9.3` and prints its note, card, note type, media, deck-config and answer-spec counts.
Answer specs are the engram extension carried in an unknown note type key, which Anki's model
API does not expose, so the script counts them from the package's own schema-11 model JSON.

```bash
.venv/bin/python verify_package.py path/to/package.apkg
```

## Learning due fixture

`learning-due.anki21.apkg` contains intraday learning, interday learning and interday relearning
cards in their home deck, suspended, buried, and in filtered decks with rescheduling on and off.
It also contains review cards in both filtered decks and an intraday relearning card in the
rescheduling filtered deck. Anki's scheduler creates the states and rebuilds the filtered decks.
The golden records package scheduling columns, collection creation time and Anki's imported deck.
For timestamp due values it records Anki's reported due timestamp. It omits that API value for
day numbers because Anki anchors it to the importing collection's current day and wall clock.

## Regeneration

Run from this directory. `uv` and Python 3.13 are required.

```bash
cd tools/anki-oracle
uv venv --python 3.13 .venv
uv pip install -r requirements.txt
.venv/bin/python generate.py
```

With no arguments or with `--memory-replay`, the generator writes the memory-replay package,
golden, and boundary-control packages and golden. Pass `--memory-rules` to regenerate only the
six replay-rule packages and their golden. Pass `--all` to regenerate the full set including those
rules (except learning-due). From the
repository root, the determinism check for the other fixtures is below. It regenerates fixtures
in place; preserve any fixture changes you need before running it.

```bash
(
  set -e
  set -o pipefail
  checks=$(mktemp -d tools/anki-oracle/.checks.XXXXXXXX)
  trap 'rm -rf "$checks"' EXIT
  find internal/notetype/testdata/anki -maxdepth 1 -type f ! -name 'memory-replay*.anki2.apkg' ! -name 'memory-replay-controls.golden.json' ! -name 'memory-replay-environments.golden.json' ! -name 'memory-replay-rules.golden.json' -print0 | sort -z | xargs -0 sha256sum > "$checks/fixtures.sha"
  (cd tools/anki-oracle && .venv/bin/python generate.py --all)
  sha256sum -c "$checks/fixtures.sha"
  git status --short internal/notetype/testdata
)
```

The checksum command must report every listed file as `OK`, including the original
`memory-replay.golden.json`. The check excludes all memory-replay packages and the controls,
environments and rules goldens. These timing goldens record the actual measurement time and timing
configuration, and the packages contain runtime-generated IDs. Compare the excluded files' contents
and imported behaviour semantically instead of byte-for-byte.
The status command may report these files even when their semantics are unchanged.

The generator leaves `learning-due.anki21.apkg` and `learning-due.golden.json` untouched by default.
Pass `--rebuild-learning-due` to regenerate the pair together when its rule changes. The golden
records the committed package, and the checksum check includes both files.

Anki fuzzes the one-minute learning step. With the card IDs and collection creation time fixed
before answering, two runs measured the following due-minus-review offsets in milliseconds, in
home, suspended, buried, filtered-on and filtered-off order: 59988, 60987, 72986, 59985, 71984;
and 59484, 60483, 72482, 59481, 71480. Within each run the five review IDs are 1 ms apart, but
their due timestamps span 13 seconds. The per-card fuzz pattern repeats with fixed IDs, while the
fractional answer-time second shifts the offsets. The package and golden cannot be reproduced byte
for byte by this generator; the default check preserves the recorded pair rather than rebuilding it.

`generate.py --table` prints the rule table below, so the table and the fixture catalogue cannot
drift apart.

Each rendering package is imported back into a fresh collection at the end of the run, and the note guids
and card count must match its golden. A package that cannot be imported fails the run.

`notetype-import` is the one fixture whose package is not written by the exporter untouched.
Anki's exporter keeps only the note types an exported note refers to, so a package it writes never
carries an unused one. Packages written by older exporters did carry them, and the note types an
importer creates from such a package is what this fixture pins. The generator therefore copies the
unused note type's rows from the source collection into the exported database before the ids,
timestamps and ZIP are normalised, so that rendering fixture is deterministic.

The media files (`placeholder.png`, `placeholder2.png`, `placeholder.wav`, `placeholder2.wav`)
are generated as fixed bytes. A package carries only the media its own notes reference.

The `image-occlusion` group is built through Anki's image-occlusion API
(`Collection.add_image_occlusion_note`), not by assigning the note fields directly. That API writes
the image, the note type's `Image` and `Header` fields, and the cards Anki generates from the
occlusion field, so the golden records Anki's own field writing. `oi=1` is the inactive-mask flag:
a note that carries it on its shapes is in "hide all, guess one" mode, and a note without it is in
"hide one, guess one" mode. The fixture has one note per shape kind (`rect`, `ellipse`, `polygon`,
`text`), one note with two shapes under one cloze number, and one note whose shapes all carry
`oi=1`.

## Golden JSON

`memory-replay.anki2.apkg` is a legacy scheduling fixture derived from the stock package. It
carries partial review, reset, lapse, relearning, repeated-learning, manual scheduling,
filtered-deck and subday histories without stored FSRS memory states. The Set due date, Forget
and filtered-off control rows come from Anki operations. After import Anki leaves `cards.data`
as `{}`; the golden records
`compute_memory_state()` on each imported card, not stored values.

Measured on the pinned oracle, `review-easy` produces stability `177.0900421142578` and difficulty
`3.0119054317474365`; SM-2 initialized from its first row's interval 30 and factor 2500, followed
by the remaining Easy ratings at 10 and 30 days, produces `177.08998536439944` and
`3.0119035440777` with go-fsrs. Changing that first row's `lastIvl` or rating did not change the
oracle result, while changing its interval or factor did. `review-lapses` produces
`0.49299123883247375` and `9.558306694030762`; the same SM-2 start followed by Again at 10 and
1 days produces `0.49299134736533484` and `9.558306728603702`. `relearning-start` produces
`1.0` and `8.215851783752441`: its first row has a negative interval and its second has interval
1 and factor 2500. In the measured histories, `set-due` and `filtered-off` match
`learning-reviews` at `63.200775146484375` and `2.1043312549591064`; `forget` produces
`20.0` and `6.413895130157471`. All 14 original golden states and 49 control measurements match
the Go importer within `1e-4` on SQLite and PostgreSQL. This establishes alignment for these
fixtures, not for every possible history or deck configuration.

The `subday` rows have Unix millisecond timestamps `1699920000000` and `1700002800000`
(2023-11-14 00:00 and 23:00 UTC). Anki returns `7.315299987792969` and
`2.1112141609191895`; the attempted Go replay with importing user timezone UTC and cutoff 00:00
returned `2.3065` and `2.11121423578539`. That implementation was reverted: calendar-date
truncation placed both reviews in the same bucket, unlike Anki's measured result. The controls below measure a 04:00
local learning-day boundary in the configured Shanghai collection. The observed current collection
`next_day_at` was `1793563200`; that value alone does not prove the historical cutoff. The
Go replay uses the importing user's current UTC offset and cutoff to match the target collection.
The comparison tolerance remains `1e-4` and has not been relaxed.

The memory replay generator fixes the process timezone to `Asia/Shanghai` and sets rollover to
04:00 on the source and importing collections. It restores the process timezone afterward. Each
`memory-replay-control-*.anki2.apkg` holds one control, so different cards can use the same exact
revlog timestamp despite the revlog primary key. `memory-replay-controls.golden.json` maps each
package to its local timestamps, Unix milliseconds, and imported `compute_memory_state()` result.
The review-start controls have two Good type 1 rows, factor 2500, interval 30; their last
intervals are 10 and 30. The learning-start millisecond controls have a Good type 0 row with
interval 1 followed by a Good type 1 row with interval 3. Each control card has type 2, queue 2,
interval 30, factor 2500, and no stored memory state.

On the pinned oracle, the one-hour controls beginning at 02:00, 02:30, 03:00, 04:30, 05:00,
and 23:30 have stability 30; those beginning at 03:30 and 04:00 have stability
32.14255905151367. For the controls beginning at 06:13, elapsed intervals of 1, 6 and 12 hours
have stability 30; 23, 24, 25 and 36 hours have stability 32.14255905151367; 2 days have
stability 34.21629333496094; and 10 days have stability 48.76170349121094. The six second
controls measure 30 at 03:00:00→03:59:59 and
03:59:59→04:00:00, 32.14255905151367 at 03:00:00→04:00:01,
03:59:59→04:00:01 and 04:00:00→04:00:01, and 30 at 04:00:01→05:00:00.
The review-start controls measure difficulty 6.08253288269043. These results place exactly 04:00:00 on the
earlier side for these histories. The proposed `floor((local_seconds - 4h) / 86400)` assigns that
instant to the later side, and disagrees at 03:00→04:00 and 04:00→05:00. The controls do not
establish a general rule for all timezones, daylight-saving transitions, or cutoff settings.

The millisecond controls test review and learning starts at 03:59:59→04:00:00.999 and
03:59:59→04:00:01.000: the first is same-day, the second is one day. Anki truncates each
revlog millisecond timestamp to seconds and computes `age = max(0, (next_day_at - seconds) / 86400)`
with integer division; delta is the previous age minus the current age. Consequently a simple
floor of local time minus the cutoff assigns the exact boundary incorrectly. `next_day_at` comes
from the importing collection's rollover and current UTC offset, not the source collection. The
environment goldens record the actual timing, offset and measurement time. Separate processes
measure Shanghai, UTC and New York configurations; New York winter and summer histories test the
current fixed offset against historical daylight-saving offsets. The importer's user timezone and
cutoff supply the equivalent settings in engram; an unset user cutoff defaults to 04:00.
Replay scans backward to the last learning run or, for incomplete history, the earliest interday
grade after a reset. Cramming rows are ignored, and manual scheduling with a nonzero factor is not
a reset. Complete history starts empty; incomplete history uses the first selected grade's interval
and factor for its SM-2 starting state and does not replay that grade. Anki's ignore-revlogs-before-date setting has no
importer equivalent and is not modelled.

Six additional controls are generated with `--memory-rules`: incomplete histories beginning with
intervals -86399, -86400 and -86401 seconds, and three histories whose first row is generated by
Anki with FSRS enabled (Hard, Good and Easy). The generator retains each generated row's rating,
interval, last interval, factor and type, fixes its timestamp, adds a later review, and removes
the card's stored memory before importing and calling `compute_memory_state()`. The measured
factors are 557, 224 and 100; the generator records the original rows in the golden and prints
both the original and imported histories. The negative interval controls use synthetic rows with
factor 2500. At -86399 Anki returns S/D 5.0 / 7.3596696853637695; at -86400 and -86401 it
returns 6.0147705078125 / 8.202864646911621. These measurements do not establish behaviour for
invalid factors outside 100..1100.

### Memory replay measurement method

The review-start controls isolate SM-2 initialization, while learning-start controls exercise
replay from an empty state. Fixed absolute timestamps are measured under multiple importing
timezones and rollovers to investigate configuration effects separately from elapsed-time effects. Each
timezone runs in a separate process; the generator sets and reads scheduling preferences and
prints the rollover and scheduler timing for the importing collection. In this investigation,
612 independent measurements covered three timezones and rollover hours 0, 4 and 6; the
re-runnable committed goldens contain 43 timing controls and six rule controls. Timing metadata records the actual
run, so compare that metadata separately from the computed values across runs. Environments 0–5
all have stability 30 and difficulty 6.08253288269043; their S/D values do not distinguish the
timezones or rollovers. The Go controls assert the recorded offset and `next_day_at` for each
configuration as well as S/D. The New York winter and summer controls additionally constrain
replay under the measured current offset despite different historical offsets.

At 03:59:59→04:00:00.999, review-start S/D is `30.0 / 6.08253288269043` and learning-start
S/D is `2.30649995803833 / 2.1112141609191895`. At 03:59:59→04:00:01.000, review-start
S/D is `32.14255905151367 / 6.08253288269043` and learning-start S/D is
`7.315299987792969 / 2.1112141609191895`. With New York rollover 0 and current offset −05:00,
the 2024 winter and summer controls at 04:30→05:30 UTC both measured
`32.14255905151367 / 6.08253288269043`, despite their differing historical local offsets.

`rslib/src/scheduler/fsrs/memory_state.rs`, `rslib/src/revlog/mod.rs`,
`rslib/src/scheduler/timing.rs`, and `rslib/src/scheduler/mod.rs`.

  Anki's importer added when it imported the package into an empty collection, in the order
  `models.all()` returned them. It records that a note type no note uses is not created.
- `note_types` repeats the note type definition the fixture needs to be rendered. A Go test can
  build the note type from this block instead of importing a package. An entry carries the full
  legacy config Anki reports: the CSS, the sort field index, the LaTeX pre/post strings and
  `latex_svg`, the Anki stock kind it was created from (or `null`), and every field and template
  option. Anki's numeric note type, field and template ids are omitted because engram assigns its
  own ids; the order is the `ord` value on each entry. `fields` is ordered by `ord`, and `templates`
  likewise. `tag` is Anki's nullable field tag value (`null` or a non-negative integer).
- `notes` is sorted by guid. `fields` maps field name to the stored field value.
- `cards` is sorted by ordinal and has one entry per card that exists in the package.
  - `id` is the card id, so a renderer test can feed `{{CardID}}` the same value.
  - `question_html` and `answer_html` are `card.question()` and `card.answer()`: the note type
    CSS in a `<style>` prefix, then the rendered side. One host name is rewritten, see
    "Documentation host" below; nothing else differs.
  - `question_css` is the CSS on its own, as returned next to the rendered nodes.
  - `question_nodes_text` and `answer_nodes_text` are the rendered side before audio/TTS
    extraction: Anki's `[sound:…]` and `[anki:tts …]…[/anki:tts]` tags are still in place. The
    same host-name rewrite applies.
  - `question_av_tags` and `answer_av_tags` list the extracted tags in document order, in Anki
    syntax. A sound tag is `[sound:<name>]`; a TTS tag is
    `[anki:tts lang=<lang> voices=<v1,v2> speed=<float> <other args>]<field text>[/anki:tts]`,
    with `voices` omitted when empty, and unknown options kept verbatim after `speed`.
  - `question_av_tags_parsed` and `answer_av_tags_parsed` are the same tags as objects:
    `{"kind": "sound", "name": …}` or
    `{"kind": "tts", "field_text": …, "lang": …, "voices": […], "speed": …, "other_args": […]}`
    in which the options are separated and the speed keeps its numeric value.
- `cardgen_expected_ordinals` is the card set Anki generates from the note content, computed with
  Anki's own renderer: one card per normal template whose front renders non-empty, one per cloze
  number for a cloze note type. `cards` may hold one more card than this list for a note whose
  fields produce no text at all; see the notes below.
- `cloze_numbers` is the sorted set of cloze numbers in the note's fields, present on cloze note
  types only.
- `cloze_typing` is the per-ordinal text `extract_cloze_for_typing` returns, present when the note
  feeds `type:cloze` comparison. It is the expected text the user has to type.
- `compare_answers` holds one entry per listed input: the note guid, the expected text, the
  typed text, the `combining` flag, how the expected text was obtained (`field:<name>` or
  `cloze:<name>`), and Anki's `<code id=typeans>` output.

Card ids, note ids, note type ids and deck ids are fixed values written by the generator, so a
golden can be compared byte for byte and a renderer can be given the same ids.

## Determinism

The default invocation generates memory-replay fixtures with runtime IDs and timing metadata;
two default runs are not required to produce identical bytes. Non-memory-replay fixtures use
the byte-level checksum check in "Regeneration". Memory-replay fixtures are compared semantically:
compare golden memory values and the rules their histories exercise, not package bytes or runtime
metadata. The original `memory-replay.golden.json` is a stable numeric-only exception and remains
in the checksum check; the controls, environments and rules goldens contain runtime metadata.

Anki assigns note, card, note type and deck ids from the wall clock and stamps modification times
on every write, so a package built twice is not byte-identical by itself. For the byte-checked
regenerated fixtures other than `learning-due`, the generator removes sources of variation as follows:

1. Note ids, card ids, note type ids and deck ids are rewritten to fixed sequential values, and
   `col.crt`, `col.mod`, `col.scm`, `notes.mod`, `cards.mod`, `cards.due`, `usn` are replaced with
   constants. The `col.`/`config`/`notetypes` JSON and protobuf blobs are rewritten with the same
   id map (`curModel`, `curDeck`, `activeDecks`, per-deck and per-note-type "last used" hints).
2. Field and template ids, which Anki draws from a random source and stores in the note type data,
   are assigned by the generator before any note is added.
3. The collection is reopened after it is normalised and only then is HTML rendered, so an
   embedded id (`{{CardID}}`) is stable in the goldens.
4. The database of each exported package is normalised the same way and vacuumed. Package exports
   can leave the field and template rows of note types they dropped behind; those rows are
   deleted, because they carry wall-clock ids.
5. The `collection.anki2` fallback is rebuilt as a fixed minimal collection: one stock note type,
   one deck, one note.
6. The modern database is recompressed with `zstandard` at level 19 with fixed frame parameters;
   media files are renumbered in name order and their mapping is rewritten.
7. Each archive is rewritten with a fixed entry order and a fixed entry timestamp
   (1980-01-01 00:00:00).
8. The golden JSON is written with sorted keys, a fixed indent and a trailing newline.

The included fixtures are checked for byte identity in "Regeneration". Regenerating on
a different machine, or after `uv` resolves new versions of the pinned dependency's own
dependencies, can change the bytes; the check is about the same environment.

## Behaviour this oracle records

- **`card.question()` and `card.answer()` contain play markers, not replay buttons.** Anki's
  Python package replaces `[sound:…]` and `[anki:tts …]…[/anki:tts]` with
  `[anki:play:<side>:<n>]`, and the web frontend turns those markers into the replay-button
  markup. The markup itself is not reachable from the package, so the golden pins the marker
  positions and the tag list, and a renderer that emits the markup is compared on its
  marker-to-tag correspondence.
- **LaTeX generation is disabled.** `renderLatex` stays off, so `[latex]`, `[$]` and `[$$]`
  render as `<img class=latex alt="…" src="latex-<sha1>.png">` plus Anki's "LaTeX image
  generation is disabled in the preferences." text. The golden therefore pins Anki's file-name
  rule, not a rendered image. Enabling it would call the host's TeX toolchain and put temporary
  paths into the output, which is neither deterministic nor portable.
- **`is_empty` means "no field contributed text".** A template whose front is only literal markup
  (`[]`, `<br>`, comments) is still empty, and a note whose fronts are all empty still receives a
  card: Anki's add-note path creates the card for template 0 when nothing else generates a card.
  That card is empty by definition, which is why `cardgen_expected_ordinals` can be `[]` while
  `cards` holds ordinal 0 (`cardgen-no-front`).
- **Cloze numbers come from every field, and that is the ported rule.** Anki 26.09.3 generates a
  cloze card for a number found in any of the note's fields, including a field that no template
  renders; such a card's front then renders empty (`cardgen-cloze-other-field`). The filter
  `{{cloze:X}}` decides what is displayed, not what is generated. A port must not narrow this to
  the fields a template references: `cardgen_expected_ordinals` in the golden is the authority,
  and it is computed from `Note.cloze_numbers_in_fields()`.
- **`{{CardFlag}}` is only recorded for an unflagged card** (`flag0`), because engram fixes the
  value to `flag0` and does not model Anki's flags.
- **Empty front.** A card whose rendered front has no field text also receives Anki's
  "The front of this card is blank." paragraph in `question_html` and `answer_html`. That
  paragraph is Anki's, apart from the documentation host noted below, and is compared like any
  other HTML.

## Documentation host

Anki's blank-front paragraph links to its help site, and that link puts a real domain into a
committed fixture, which the repository rules forbid. The help-site host is read from
`anki.consts.HELP_SITE` in the pinned package, never repeated in this repository, and the
generator rewrites it to `https://docs.ankiweb.invalid` in the four fields that can carry
rendered output: `question_html`, `answer_html`, `question_nodes_text` and `answer_nodes_text`.
The reserved `.invalid` TLD cannot resolve, so the rewritten link is inert.

No other byte of Anki's output changes: the surrounding text, tags, attributes and ordering stay
as Anki wrote them. `write_json` asserts that the serialised golden contains no occurrence of the
help-site host and that the placeholder is the only documentation host in the file, so a run fails
instead of writing a fixture with a real domain if a future Anki release adds another host. The
packages store note field values, not rendered output, so they carry no host name.

## What is not covered

- Template error codes. Anki renders its own English error text for an unknown field, an unclosed
  conditional or a missing cloze number, while the Go ports return stable error codes the caller
  localises. The error text is not a contract, so no fixture records it.
- Scheduling beyond `memory-replay` and `learning-due`, deck configuration beyond the FSRS weights
  in `weights`, and browser-only rendering. The rendering packages omit scheduling and deck configurations.
